# 令牌桶确定性并发测试方案与详细案例

> 版本：rate-limiting deterministic concurrency delta
> 创建日期：2026-08-28
> 对应 Phase 2 Spec：`specs/rate-limiting/spec.md`

## 一、测试策略

### 1.1 测试金字塔

本变更以快速、确定性的 `TokenBucket` 单元测试为主体；以现有
`RateLimitMiddleware` 单元/轻集成测试保护 HTTP 与配置兼容；最后以 Python
3.10～3.12 的完整项目质量门提供跨版本回归证据。不新增依赖真实网络或 wall clock
的 E2E 测试。

### 1.2 测试原则

- 所有时间相关断言由测试持有的单调时钟驱动，测试不等待真实时间。
- 原子消费、补充公式、容量上限、锁等待和默认兼容分别验证，避免一个失败掩盖另一个。
- 严格 RED→GREEN→REFACTOR；新增测试节点先失败，再做最小实现。
- 三版本环境缺失或失效必须显式报告，不能以 skip 或空命令形成假绿。
- TC-ID 全局唯一；保留既有并发案例编号 005，新增使用空闲的 007～011。

| 测试文件 | 用例数 | 类型 | 覆盖范围 |
|----------|--------|------|----------|

## 二、详细测试案例

### 功能 1：冻结时间并发消费

#### 案例 1.1 — 初始 burst 是冻结时间下唯一可消费额度

| 字段 | 内容 |
|------|------|
| **ID** | TC-RL-005 |
| **对应 Spec** | SC-RL-007 |
| **优先级** | P0 |
| **预置条件** | FakeClock 冻结；rate=1000、burst=5；同一桶被 50 个协程共享 |
| **输入** | `asyncio.gather` 并发执行 50 次 `consume()` |
| **预期结果** | 恰好 5 次成功；token 不为负；结果与实际执行时长无关 |
| **当前状态** | ❌ 现有测试使用真实时钟，需重写 |

### 功能 2：锁序列化证据

#### 案例 2.1 — consume 在已持锁时等待

| 字段 | 内容 |
|------|------|
| **ID** | TC-RL-007 |
| **对应 Spec** | SC-RL-011 |
| **优先级** | P0 |
| **预置条件** | FakeClock 冻结；桶有 token；测试先持有桶的消费锁 |
| **输入** | 调度 `consume()`，让出事件循环，随后释放锁 |
| **预期结果** | 释放前任务未完成且 token 不变；释放后原子消费成功且 token 非负 |

### 功能 3：可控时间补充

#### 案例 3.1 — rate × elapsed 精确补充

| 字段 | 内容 |
|------|------|
| **ID** | TC-RL-008 |
| **对应 Spec** | SC-RL-008 |
| **优先级** | P0 |
