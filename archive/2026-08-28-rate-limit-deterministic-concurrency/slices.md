## Five-step Analysis

1. **依赖图**：1 node / 0 edge / 1 zero-dependency / 0 cycle。
2. **风险评分**：rate-limiting 得分 4（安全关键 + 6 scenarios + 修改内部构造边界），高风险。
3. **工作量**：总计 6 TC、2 个主要代码/测试文件及多版本验证，整体 L；拆成 M + S + M。
4. **智能分组**：时间注入/补充放在 S1；锁证据单列 S2；环境证据单列 S3。
5. **并行建议**：理论上单 capability 是零依赖，但共享文件和严格 RED/GREEN 顺序使串行更安全。

## Rationale

### Slice S1：可控时钟与补充契约（P0，先行）

- **依赖关系**：无；为其余确定性测试提供 FakeClock 和生产默认兼容边界。
- **风险分析**：`EXP-2026-0011`、`EXP-2026-0014` 要求隔离真实时间/环境噪声；错误实现可能改变生产 refill。
- **工作量估算**：M，4 个 TC、一个生产文件和一个测试文件。
- **完成门**：先看到新增/重写测试在旧实现上 RED，再做最小 GREEN；定向回归全绿。

### Slice S2：锁等待与原子消费证据（P0，串行）

- **依赖关系**：使用 S1 的冻结时钟，避免持锁断言夹带时间补充噪声。
- **风险分析**：限流超耗属于安全风险；白盒锁检查是设计确认的 L3 锚点。
- **工作量估算**：S，1 个 TC；现有实现预期已满足，产品代码可能无需变化。
- **完成门**：RED 必须能在移除锁的受控证据下区分失败，当前实现上 GREEN 且 token 不变式成立。

### Slice S3：多版本与完整质量门（P1，最终）

- **依赖关系**：只验证已完成行为，不先于 S1/S2。
- **风险分析**：`EXP-2026-0006`、`EXP-2026-0022` 要求真实节点与唯一 TC；环境缺失不得假绿。
- **工作量估算**：M，1 个矩阵 TC，但包含三解释器、完整 pytest、coverage、Ruff、Mypy。
- **完成门**：所有可用的三版本真实环境明确通过；任何不可用环境单独报告；项目质量门保持通过。
