# Python 3.11 令牌桶并发测试确定性 - 技术设计

## Context

`TokenBucket` 使用连续补充模型：每次 `consume()` 在 `asyncio.Lock` 内根据
`time.monotonic()` 的经过时间补充 `rate × elapsed` 个 token，再尝试消费。
现有 `TC-RL-005` 以 `rate=1000` 启动 50 个协程，并断言恰好只有初始
`burst=5` 个成功；当测试执行超过 1ms 时，第 6 个 token 已合法补充，因此该断言
在 Python 3.11 上会非确定性失败。

本变更只收敛 `TokenBucket` 的内部时间边界和测试证据。公开的 `rate`、`burst`、
`per`、HTTP 429、`Retry-After` 及 middleware 构造路径保持不变。支持范围仍是
Python 3.10、3.11、3.12，并严格执行 RED→GREEN→REFACTOR。

经验库交叉检查采用以下约束：

- `EXP-2026-0011`、`EXP-2026-0014`：质量证据必须来自可比较的真实环境；单元测试
  不得把主机速度或真实时间流逝误判为产品回归。
- `EXP-2026-0006`、`EXP-2026-0022`：Agent checkpoint 必须绑定真实、稳定、全局
  唯一的测试节点与 TC-ID，不使用失效路径或空 glob。

|------|---------------|-----------|---------|

## Decisions

### 1. 为 TokenBucket 注入可控的单调时钟

**方案**：将构造函数扩展为 `TokenBucket(rate, burst, *, clock=None)`。实例保存
`self._clock`；未提供时使用 `time.monotonic`。初始化 `_last_refill` 和后续
`_refill()` 均调用该实例时钟。测试使用只在显式调用 `advance()` 时前进的
`FakeClock`。

**为什么**：这保留生产连续补充语义，同时让测试可以独立控制 elapsed，消除主机
性能、解释器版本和事件循环调度速度对断言的影响。keyword-only 参数避免误把第三个
位置参数当成既有公开契约。

**备选方案及排除原因**：

- 将成功数放宽为 5 或 6：会弱化并发安全 oracle，且不能证明 token 永不超耗。
- 降低测试 rate：仍依赖真实时间，只是延长触发窗口。
- 全局 monkeypatch `time.monotonic`：会污染同进程中的其他测试和库。
- 改为离散补充或修改生产算法：超出本变更范围，并可能改变公开限流语义。

### 2. 分离冻结时间并发证据与时间推进证据

**方案**：重写 `TC-RL-005`，在冻结时钟下发起 50 次并发消费，断言恰好
`burst` 次成功且 token 非负；新增测试分别显式推进时钟并验证 `rate × elapsed`、
验证补充不超过 `burst`。

**为什么**：原子性、补充公式和容量上限是三个不同的失败面。拆分后每个失败都有
单一、可诊断的原因，且不会用冻结时钟掩盖连续补充实现错误。

**备选方案及排除原因**：

- 在一个大测试中覆盖全部行为：失败定位不清，容易再次把时序和原子性耦合。
- 直接写内部 token 值驱动测试：会绕开补充行为，证据不足。

### 3. 用持锁等待证明 consume 确实受序列化保护

**方案**：测试先持有桶的现有锁，再调度 `consume()`；在释放锁前断言任务未完成且
token 未变化，释放后断言消费按预期完成。

**为什么**：`asyncio.gather()` 本身不能充分证明锁存在，因为当前临界区内部没有
其他 `await`，即使误删锁，协程也可能在单线程事件循环中表现为顺序执行。持锁等待
测试直接锚定序列化边界。

**备选方案及排除原因**：

- 仅保留 gather 计数断言：可以验证结果，但不能敏感地检测锁被移除。
- 引入线程压测：当前实现契约是事件循环安全，线程模型超出范围且更易产生环境噪声。

### 4. 多版本验证作为独立验收检查点

**方案**：在 Python 3.10、3.11、3.12 上重复执行 rate-limit 定向测试，并在
Phase 5 运行项目完整 pytest、Ruff、Mypy 和覆盖率门。验证使用项目真实隔离环境，
不可用的解释器或环境必须显式报告，不能静默跳过。

**为什么**：问题只在特定解释器/运行速度组合中暴露，单版本通过不能闭合成功标准。

**备选方案及排除原因**：

- 只依赖当前默认 Python：无法证明项目声明的三版本兼容性。
- 只依赖远程 CI：会延迟 RED/GREEN 反馈；本地可用环境应先提供快速证据。

## Architecture

```text
production                                      deterministic tests
──────────                                      ───────────────────
RateLimitMiddleware                             FakeClock(now=0)
        │                                               │
        └── TokenBucket(rate, burst)                    └── TokenBucket(
                │                                            rate, burst,
                ├── clock = time.monotonic                  clock=fake_clock)
                └── asyncio.Lock                              │
                     │                                        ├── frozen: concurrency
                     └── refill → atomic consume              └── advance: refill/cap
```

调用链保持为：middleware 获取维度 key → 获取/创建桶 → `await consume()` → 在同一锁内
读取时钟、补充、判定和扣减 → 返回 allow/reject。时钟对象不进入配置、HTTP、日志或审计
边界。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 可注入时钟返回倒退时间 | 延续现有 `elapsed > 0` 行为，不补充、不回退 `_last_refill`；本变更不扩大异常时间策略。 |
| 测试过度依赖 `_lock` 私有字段 | 这是 L3 安全锚定的有意白盒检查；实现若更换为等价序列化机制，必须显式调整设计和测试。 |
| 冻结时钟掩盖 refill 缺陷 | 使用独立的精确推进与 burst cap 测试覆盖 refill。 |
| 三版本环境不可用导致假绿 | 缺失环境显式记为阻塞/待验证，Phase 5 不将其计为通过。 |
| 新依赖点意外改变 middleware | 默认时钟兼容测试及完整 middleware 回归确保无公开契约变化。 |
