# 设计调整说明

> 原始设计基线：Phase 2 的 `design.md`、`specs/*.md` 与 `test-plan.md`

## 调整汇总

Phase 4 没有设计偏离。Phase 5 文档审查发现一个未在 Phase 2 基线中显式覆盖的边界事实：
活跃运行时代码的 docstring/comment 仍包含内部实现阶段使用的 `v0.3.0` 标签。该标签不是公开
里程碑声明，但如果不分类，会让源码检索结果产生歧义。

本次采用轻量边界调整：

- 在 `DESIGN.md` 的历史证据分类中增加“活跃运行时代码内部注释”类别，明确其只记录原内部
  实现标签，不代表公开 v0.3.0 里程碑已交付。
- `TC-RMAP-007` 精确校验分类表，并扫描当前包含该标签的运行时模块集合。
- 不修改任何运行时代码；这符合 Gate 2 后用户确认的文档与契约测试范围。

后续应在独立 STDD change 或首个 v0.3.0 实施 change 中清理这些内部注释，使源码搜索结果也
直接采用统一版本语义。

Phase 6 归档后复验发现第二项轻量生命周期调整：`specs/project-docs/spec.md` 是累积式主规范，
正常 Deliver 会追加当前 change，因此不能用“工作区必须完全干净”证明旧要求未被改写。保护
方式调整为显式断言既有 REQ-DOCS-011/012/013 仍存在；真正不可变的 archive、canonical
历史文件、config spec 和 Release Notes 继续使用 Git status 边界保护。

## 原则复核

该调整不改变插件、Flow、运行时策略、协议契约或数据处理，只提高版本证据的显式性和可审计
性。保留旧注释是授权边界内的有意取舍，限制及后续修复路径已明确记录。首次非插桩全量回归
触发已知宿主微基准假失败，按既有 EXP-2026-0011 使用 CI 同构 coverage 质量命令验证，没有
修改性能规格或测试门槛。

Phase 6 调整只修正文档契约的归档生命周期语义，不改变 Gate 3 已确认的范围、产品行为或原则
结论；交付后重新执行文档契约、canonical checkpoints 和全量质量门。
