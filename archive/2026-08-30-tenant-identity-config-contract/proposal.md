## Why

v0.3.0 已确定为多租户安全策略隔离基础，但当前网关只有 API Key 名称， 没有可信、稳定且可验证的租户身份契约。若直接实现租户级 Flow 或策略解析， 可能出现租户身份伪造、配置歧义或静默落入其他租户策略。


## What Changes

- 建立有界、非秘密、稳定的租户标识与配置 schema
- 将 API Key 等可信认证结果显式绑定到租户，禁止依据客户端自声明 Header 直接信任租户身份
- 建立请求级、不可变的租户身份上下文，供后续 v0.3.0 changes 消费
- 在启动阶段拒绝重复租户、悬空绑定、矛盾默认租户及其他歧义配置
- 对缺失、未知或无法解析的租户身份提供明确、可观测的失败行为，禁止静默跨租户回退
- 保留现有单租户配置入口，未启用多租户时无需迁移即可继续工作
- 更新配置、认证和请求上下文契约的规格、示例及测试

### New Capabilities

- **tenant-identity-context**：从可信认证结果解析并传播唯一、稳定且不可变的请求级租户身份
- **tenant-config-contract**：定义租户声明、身份绑定、默认入口与启动期一致性校验

### Modified Capabilities

- **api-key-authentication**：认证成功结果可以关联租户，但不得泄露凭据或信任客户端自声明租户
- **config-system**：支持多租户配置 schema，同时兼容现有单租户配置

## Success Criteria

- [ ] 租户身份只能来自经过验证的服务端配置和可信认证结果
- [ ] 客户端不能通过自声明租户 Header 越权切换租户
- [ ] 每个成功认证的多租户请求都获得唯一、稳定、不可变的租户上下文
- [ ] 重复租户、悬空认证绑定和歧义默认配置在启动阶段被拒绝，并给出脱敏错误
- [ ] 未知或无法解析的租户不会落入其他租户或共享默认策略
- [ ] 现有单租户配置无需修改即可加载，现有请求协议和行为保持兼容
- [ ] 租户标识受到格式、长度和基数入口约束，且不得包含或暴露认证密钥
- [ ] 新增单元、集成和失败路径测试；全量 pytest、ruff、mypy 通过，覆盖率不下降
- [ ] 不提前实现后续三个 v0.3.0 change 的能力
